# خطة تثبيت واعتمادية ساعة المسجد ESP8266

> الهدف: الوصول إلى Firmware يعمل 24/7 بدون Reset أو WDT أو تقطيع ملحوظ في
> شاشة P10، مع حماية الإعدادات وإمكانية رجوع آمنة عند فشل التحديث.
>
> **قاعدة تشغيل:** لا Upload ولا مسح Flash ولا كتابة على الجهاز حتى يكتب المالك
> صراحةً: **ابدأ** ويؤكد أن ESP8266 موصول بالكمبيوتر.

## 1. النطاق والنتيجة المطلوبة

تشمل الخطة مسارات الإقلاع، RTC/I2C، الشاشة، حساب الصلاة، Wi-Fi AP وHTTP،
EEPROM، OTA، الذاكرة، WDT، واختبار العتاد. لا تشمل إعادة تصميم تطبيق الهاتف أو
تغيير توصيلات الشاشة إلا إذا كشف اختبار العتاد مشكلة فعلية.

معايير النجاح النهائية:

- إقلاع متكرر بدون Exception أو Reset loop سواء كان DS3231 موجودًا أو مفصولًا.
- استمرار الساعة والعرض عند تعطل Wi-Fi أو I2C ثم التعافي دون تجميد النظام.
- صحة انتقالات الأذان والإقامة والنوم والأذكار، بما فيها الجمعة ومنتصف الليل.
- عدم وجود مدخل HTTP قادر على إخراج قيمة عن نطاقها أو فهرسة مصفوفة خطأ.
- عدم انخفاض `MaxFreeBlockSize` أو ارتفاع Heap fragmentation باستمرار تحت الحمل.
- نجاح OTA الصحيح وفشل OTA المقطوع أو غير الصحيح بصورة آمنة.
- نجاح اختبار تشغيل متصل لا يقل عن 24 ساعة أولًا، ثم Soak test ممتد 7 أيام.

## 2. خط الأساس المثبت

تم القياس في 2026-09-01:

| البند | النتيجة |

| بيئة ESP8266 | `esp12e`, Arduino Core 3.1.2, Platform 4.2.1 |
| بناء Firmware | ناجح |

هذه الأرقام هي مرجع المقارنة بعد كل مرحلة. لا يقبل ارتفاع RAM أو Flash دون سبب
واضح وموثق.

## 3. قواعد التنفيذ

1. إصلاح سبب المشكلة في نقطة مشتركة، لا إضافة Guards مكررة عند كل مستدعٍ.
2. Commit صغير لكل مشكلة مستقلة، مع بناء واختبار قبل الانتقال لما بعدها.
3. عدم تغيير `lib/*` إلا عند الضرورة، وتوثيق أي تغيير في `docs/DECISIONS.md`.
4. لا كتابة إلى EEPROM داخل `loop()`، ولا انتظار شبكي حاجب داخل `setup()`.
5. جميع مقارنات `millis()` تكون آمنة عند rollover.
6. أي منطق جديد له اختبار runnable واحد على الأقل.
7. لا يعتمد العرض أو الصلاة على نجاح Wi-Fi أو NTP.

## 4. مراحل التنفيذ

### المرحلة 0 — Preflight وتأكيد نقطة الرجوع

تنفذ فقط بعد توصيل الجهاز وقول **ابدأ**:

- تحديد منفذ COM والتأكد من ظهور الشريحة.
- قراءة `flash_id` لتأكيد نوع اللوحة وحجم Flash قبل الرفع.
- لا تُسحب نسخة Flash من اللوحة: المالك أكد في 2026-09-01 أن لديه نسخة Firmware
  قديمة صالحة للرجوع، وطلب تجاوز النسخ الاحتياطي لتوفير الوقت.
- حفظ الإعدادات الحالية من `/getData` إن كان الـFirmware القديم يعمل.
- التقاط Serial boot log وReset reason بسرعة 115200.
- بناء النسخة الحالية مرة أخرى وحفظ ملف `updateP104.bin` كمرجع.
- تسجيل إصدار Git الحالي و`git status --short`.

بوابة القبول: نسخة الرجوع الخارجية مؤكدة، والمنفذ واللوحة والطاقة معروفون.

### المرحلة 1 — إصلاحات الإقلاع وسلامة الذاكرة P0

- تشغيل `rtc.begin()` قبل أي استدعاء لـ`rtc.now()`.
- جعل `effectiveBrightness()` آمنة عند غياب RTC واستخدام `timeData` الموحد.
- مراجعة كل نصوص `PROGMEM` ومنع تمريرها إلى `strlen/strcmp/strncpy/snprintf`
  أو DMD كأنها RAM.
- إضافة مسار عرض واحد للنصوص الموجودة في Flash باستخدام النسخ `_P` الصحيح.
- التحقق من الإقلاع عند وجود DS3231 وعند فصله.

بوابة القبول:

- Build ناجح والاختبارات ناجحة.
- 20 إعادة تشغيل متتالية بدون Exception.
- ظهور رسالة ضبط الساعة بدل Reset عند غياب RTC.

### المرحلة 2 — حماية Configuration وواجهات HTTP

- قراءة الطلب إلى `Configuration next = config` بدل تعديل الحالة الحية تدريجيًا.
- التحقق من الحدود الدنيا والعليا لكل حقل: طريقة الحساب، المذهب، المنطقة
  الزمنية، DST، الإقامة، النوم، السطوع، السرعة، اللغة، الإحداثيات، وتصحيح الهجري.
- رفض الطلب كاملًا عند وجود قيمة واحدة غير صالحة، دون Save جزئي.
- ضمان NUL termination وسلامة حد UTF-8 للرسالة واسم المسجد.
- إضافة `language` إلى `/getData` بعد تأكيد عقد تطبيق الهاتف.
- وضع Authentication على أوامر التعديل وOTA قبل أي نشر خارج بيئة الاختبار.

بوابة القبول: اختبارات حدود القيم تنجح، ولا يغيّر الطلب المرفوض Configuration أو
EEPROM.

### المرحلة 3 — تصحيح منطق الصلاة والحالة

- إزالة شرط كاش الإقامة الحالي أو مقارنة جميع القيم؛ النسخ المباشر هو الأبسط.
- حساب نافذة الجمعة باستخدام `sleepGomaaTime`.
- دعم النوافذ التي تعبر منتصف الليل.
- توحيد الانتقالات في حالة واضحة:
  `Normal -> PrePrayer -> Azan -> Iqama -> Sleep -> Azkar`.
- اختبار إقامة صفرية، فجر قريب من منتصف الليل، عشاء متأخر، الجمعة، وتغيير
  الإعدادات أثناء اليوم.
- مقارنة عينة أوقات الصلاة لعدة تواريخ وإحداثيات مع مرجع المالك/التطبيق.

بوابة القبول: اختبارات native لكل الحدود السابقة، وتجربة زمنية مسرعة على الشاشة.

### المرحلة 4 — RTC وI2C وWi-Fi دون حجب

- إضافة قراءة RTC تتحقق من صلاحية التاريخ والوقت قبل تحديث `timeData`.
- إعادة محاولة RTC دوريًا مع backoff عند الفشل بدل الحكم النهائي وقت الإقلاع.
- فحص `lostPower()` وإظهار حالة مفهومة دون تعطيل Web API.
- استخدام الوقت المصحح نفسه للعرض والصلاة وPower Save وDST.
- إبقاء الجهاز AP-first؛ مراقبة وضع AP وإعادة تشغيله دوريًا عند فشله دون `while`.
- إذا أضيف NTP لاحقًا: AP+STA ومحاولات محدودة، وDS3231 يظل المصدر المحلي الأساسي.

بوابة القبول: فصل وإعادة RTC أو Wi-Fi لا يوقف تحديث الشاشة ولا يسبب WDT.

### المرحلة 5 — سلاسة الشاشة وWDT وOTA

- جعل علم مؤقت DMD `volatile` بعد إثبات الحاجة على نسخة المكتبة الحالية.
- قياس أطول زمن لدورة `loop()` أثناء Scroll وHTTP وEEPROM وOTA.
- عدم تنفيذ أعمال قابلة للتأجيل داخل Handler؛ يرد Handler ثم تعالج المهمة في
  scheduler عند الحاجة.
- فحص نتيجة `Update.begin/write/end` ومعالجة `UPLOAD_FILE_ABORTED`.
- إيقاف الرسوم غير الضرورية أثناء كتابة OTA مع استمرار WDT وخطة رجوع واضحة.
- اختبار OTA ناجح، ملف خاطئ، قطع اتصال، وإعادة تشغيل بعد النجاح.

بوابة القبول: لا Flicker مستمر أثناء الإعداد العادي، ولا Boot loop بعد حالات OTA
الفاشلة.

### المرحلة 6 — EEPROM وFlash والذاكرة

- عدم `commit()` إذا لم تتغير البايتات.
- Dirty flag وCommit مؤجل واحد بعد استقرار تعديلات التطبيق.
- إضافة CRC32 إلى Configuration، مع قرار موثق إذا استلزم ذلك رفع
  `EEPROM_VERSION` ومسح الإعدادات مرة واحدة.
- استخدام نسختين A/B فقط إذا أثبتت متطلبات الموقع ضرورة النجاة من انقطاع الطاقة
  أثناء الحفظ.
- تسجيل `FreeHeap`, `MaxFreeBlockSize`, وHeap fragmentation في وضع تشخيصي.
- تحسين مخزن `/getData` فقط إذا أثبت القياس حاجة فعلية إلى 3KB إضافية.

بوابة القبول: إعادة إرسال نفس الإعدادات لا تكتب Flash، وفساد Config تجريبي يؤدي
إلى Defaults آمنة لا Crash.

### المرحلة 7 — اختبار العتاد والإطلاق

ترتيب الاختبار:

1. Upload أولي مع الشاشة مفصولة إن كانت توصيلات Boot strap غير مؤكدة.
2. اختبار Serial والإقلاع وRTC فقط.
3. توصيل P10 بمصدر 5V خارجي مناسب مع أرضي مشترك؛ لا تُغذى اللوحات من USB.
4. اختبار الخط الكبير والصغير، العربي والإنجليزي، والرسائل الطويلة.
5. اختبار الأذان والإقامة والجمعة باستخدام وقت تجريبي مضبوط.
6. اختبار تطبيق الهاتف وكل endpoints.
7. تشغيل 24 ساعة مع تسجيل Heap/Reset، ثم 7 أيام دون تعديل.

معايير Rollback:

- أكثر من Reset غير مفسر.
- تكرار WDT أو Exception.
- فقد إعدادات أو وقت.
- تقطيع واضح دائم في الشاشة.
- انخفاض مستمر في أكبر كتلة Heap حرة.

عند تحقق أي شرط: وقف النشر، حفظ Serial log، ثم إعادة نسخة Firmware القديمة
الموجودة لدى المالك.

```powershell

C:\Users\m_nag\.platformio\penv\Scripts\platformio.exe run -e esp12e

# اختبارات native على Windows
$env:Path = "C:\Users\m_nag\.platformio\packages\toolchain-gccmingw32\bin;$env:Path"

# Serial monitor لاحقًا
C:\Users\m_nag\.platformio\penv\Scripts\platformio.exe device monitor -b 115200 -p COMx
```

## 6. تعريف الاكتمال

لا تعتبر الخطة مكتملة بمجرد نجاح البناء. تكتمل فقط عندما تكون كل مراحل ملف
`RELIABILITY_PROGRESS.md` بعلامة `[x]`، ويوجد Backup، وسجل اختبار عتاد، ونتيجة
Soak test، وخطة رجوع مجربة أو مؤكدة.
